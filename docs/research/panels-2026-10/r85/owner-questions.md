# Panel F — owner queue, main asks one at a time

These questions use only exact printed, reviewed r85 forms. Their source is brief.md;
tally.md preserves the votes, objections and factual checks. Nothing is adopted yet.

## 1. Which bad field should the response identify?

TL;DR: the panel prefers naming the particular member or list element, and adopting the
exact new admission fixtures as part of that choice.

A caller sends two conflicting trust choices, or a list with one bad key. Should the
response point at the particular choice/bad key, or at the whole trust object/list?
The panel's preferred form also requires these pointers in the printed admission cases;
one reader objects that the existing rules do not already require them on that path.

- **Name the member or element (Recommended), A:** fable/astra/sol pick and accept;
  opus rejects the printed admission fixtures and prefers its distinct added-unknown-field
  version. Adopt exactly Q1-A, including its CNF paragraph, fixture file and owner pointers.
- **Name the whole group or list, B:** no first picks; fable/astra/sol accept, opus rejects
  the same fixture scope. Adopt exactly Q1-B.
- **Fix only the shown cases, D:** no first picks; fable/astra/sol accept, opus rejects the
  same fixture scope. Adopt exactly Q1-D, retaining discretion elsewhere.
- **Keep the existing discretion, C:** no first picks; astra/sol accept, fable/opus reject.
  Adopt exactly Q1-C; no new set rules or fixture assertions.

Which exact form should be adopted? Lands on WIR-9a, CNF-342 and the printed WIR-20,
WIR-35, API-13 and RSC-4 owner pointers, plus the exact q1-fixtures.json for A/B/D;
bead pv-y1zy. This is new diagnostic/test policy, not the prior wording-only precedent.

## 2. Which error should win when caller input and a generated value are both bad?

TL;DR: all participating readers pick reporting the caller's bad input first.

The caller sends a location the provider rejects. The service also generates a key name
the same validation rejects. Reporting the location lets the caller correct it; the service
defect remains and may become the next error. Reporting only the service defect hides
the known caller correction and labels the unchanged request retryable.

- **Report the caller field first (Recommended), B:** fable/opus/astra/sol all pick and
  accept; adopt exactly Q2-B and its controls/paired fixture.
- **Report the service defect first, A:** no first picks; astra/sol accept, fable/opus reject
  because the unchanged caller input remains invalid; adopt exactly Q2-A.
- **Require generated-value validation first, C:** no first picks; astra/sol accept,
  fable/opus reject. Adopt exactly Q2-C, including its new validation-stage order.

Should Q2-B be adopted? Lands on PRV-47 and CNF-342; bead pv-xzre. The exact package
preserves single-origin outcomes, no mutation, full release and error/view agreement.

## 3. Make repeated install validation explicitly finish before either marker write?

TL;DR: all participating readers pick explicit timing text plus the regression fixture.

An install was admitted with its destructive acknowledgement true, then the stored value
became false. If the worker first records that rescue may have started, and only then
rejects the acknowledgement, it cannot truthfully report the promised untouched/no-rescue
outcome. The preferred form explicitly completes all repeated validation before either
marker write and tests that attempted marker-first execution.

- **State the full timing rule and test it (Recommended), A:** fable/opus/astra/sol all
  pick and accept; adopt exactly Q3-A and its common fixture.
- **Add timing only to the present-value paragraph, C:** no first picks; all accept;
  adopt exactly Q3-C and the same fixture.
- **Keep the normative wording and add the fixture, B:** no first picks; fable/opus
  accept, astra/sol reject as an incomplete clarification of the owner's referent.

Should Q3-A be adopted? Lands on OPS-23 and CNF-34; bead pv-hups. The fixture's
conformance strength makes the whole package substantive even if the bad trace is
already excluded by the existing settlement and marker combination.
