## Sol's exact adjacent upper-bound trace

**Arithmetic verified; a clock-only PostgreSQL execution is not established.** Use exactly the supplied numbers, without substituting another example:

| Event/value | Time |
|---|---|
| Last old-history component acknowledgement | 20.0002 |
| All components stopped | 20.0003 |
| Newly begun incident transaction | 20.0004 |
| Assumed downward represented/stored r | 20 |
| Claimed clock-only allowance | 0 |
| Computed f | 20 |

Exact rationals give `20 < 20.0002 < 20.0003 < 20.0004`. The stopping order is consistent with [STO-54](https://github.com/douglaz/provisiond/blob/3c214c147021a90d4ba5a74269b8bd4adc389670/05-persistence.md#L1560): “Before the restore begins, the deployment MUST stop every engine and `api` process”, and with application:47: “The transaction begins after the existing stopping/fencing requirements are satisfied.” There is no illicit post-stop acknowledgement in this trace. If r really is 20, the acknowledgement is after f and violates application:49's upper MUST. The lost downward displacement is 0.0004; covering that displacement reaches the transaction start. Merely proving b≤f would not repair the false upper certificate.

However, application:47 defines “restore_instant is transaction_timestamp() of the newly begun transaction inserting this incident”, and application:61 retains that event timestamp. The pinned spec does **not** establish the extra operation that turns an otherwise exact result 20.0004 into stored 20. WIR-1's second-precision *wire output* is not such a storage instruction. A perfect microsecond clock and uncoarsened function result preserve 20.0004, so under that direct assignment the asserted r=20 step is refuted. A coarsened column/capture or lower-resolution platform must be specified/evidenced before claiming this exact clock-only execution. It cannot be inferred from finite precision alone.

PostgreSQL's [current-time documentation](https://www.postgresql.org/docs/18/functions-datetime.html#FUNCTIONS-DATETIME-CURRENT) identifies this function with transaction-start time; omitted precision uses the available precision. Its [date/time types](https://www.postgresql.org/docs/18/datatype-datetime.html) support microsecond resolution and optional coarser precision. The [PostgreSQL timestamp implementation](https://github.com/postgres/postgres/blob/REL_18_STABLE/src/backend/utils/adt/timestamp.c) returns the captured transaction-start value and preserves the gettimeofday microsecond field; its precision coercion is a separate operation. These sources do not turn 20.0004 into 20 merely because the type is an integer timestamp. They also do not certify the deployed platform's clock error. No database was contacted or measured.

Therefore: Sol's exact numbers are a **valid conditional counterexample to a recipe that ignores an assumed lossy conversion**, not a demonstrated conforming execution or a PostgreSQL reproduction. The candidate's unchanged upper MUST rejects the asserted f. The condition is disclosed here rather than converting the observation into a verified blocker. The same issue was flagged by the other readers; nobody's acceptance was conditioned on an event-clock edit. No event-side wording or new task is adopted in this tally. As on the lower side, f≥real-start is sufficient for the stopping-based proof, not logically necessary when stronger evidence bounds the last acknowledgement.
