**Verdict: the missing-attachment gap is real, but the proposed retention rule cannot reliably find the missing resource.**

**Why.** A Robot delete accepted with 2xx followed by a throttled listing is **not** `failed` at this commit: accepted mutations with later read errors reach `needs_reconciliation` ([03-operation-lifecycle.md:270](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L270)). A later complete sweep can record the machine gone and close its episode ([03-operation-lifecycle.md:1343](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L1343), [03-operation-lifecycle.md:1081](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L1081)). With no attachment row, `STO-18`’s “while any `billable` attachment with a null `released_at` remains” and `LDG-32`’s “every billable attachment it left behind has release evidence” are evaluated against an empty recorded set; tombstoning and commitment closure can follow ([05-persistence.md:357](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/05-persistence.md#L357), [12-billing-and-ledger.md:308](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/12-billing-and-ledger.md#L308)).

**Defects in the triage and current rules.**

- [02-provider-contract.md:528](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/02-provider-contract.md#L528) requires listing on “every delete that succeeds with the resource gone,” but specifies no durable outcome for an incomplete listing. Successful resolution is meant to have the same row effect ([02-provider-contract.md:555](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/02-provider-contract.md#L555)); the failed-listing path remains unspecified.
- A provider-terminated machine has no delete listing. A scheduled delete records a date, then waits for a later gone observation ([03-operation-lifecycle.md:1072](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L1072)). Both can reach the same empty-row closure. The sweep *does* list attachments of retained machines, contrary to the broad “no later listing” claim, but its specified write is `released_at` for a **missing existing** attachment, not insertion of an unseen survivor ([03-operation-lifecycle.md:1368](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L1368)).
- `API-65` requires an attachment row before release can be requested ([04-api-contract.md:1090](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/04-api-contract.md#L1090)). The Robot account API exposes `GET /ip` and `GET /subnet` independently of server lookup; the current sweep has no orphan comparison for them ([Robot Webservice](https://robot.hetzner.com/doc/webservice/en.html)).
- Operator loss is **conditional**, not established for every Robot delete. The repository still marks IP survival for a live test ([02-provider-contract.md:195](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/02-provider-contract.md#L195)). Hetzner says extra IPs or add-ons *may* need separate cancellation and bills IPs/subnets for time used ([Auction FAQ](https://docs.hetzner.com/robot/general/server-auction-faqs/), [Robot cancellations](https://docs.hetzner.com/general/billing-and-account-management/cancellation/cancellations-robot/)). V1 sells orders with the `primary_ipv4` add-on while charging no separate attachment customer rate ([ADR-0037:165](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/docs/adr/0037-the-billing-stop-window-is-withdrawn-and-wind-down-is-sized-to-the-gone-write.md#L165)). A tenant can initiate create/delete cycles, but neither forcing a listing throttle nor survival is demonstrated; provider termination is an accident/provider-action path. If an IP survives without cleanup, operator rent lasts until actual cancellation, with no specified end date.
