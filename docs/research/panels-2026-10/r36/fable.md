**Q19a** — Verdict: answer (3), and dissolve the local count. The reserve is a stop on new admissions, read from the provider's own `RateLimit-Remaining`, not capacity the deployment holds.

Why. (1) is refused by the ADR itself: "A later request of an admitted operation is never refused locally, or the budget would recreate the throttled poll" (`docs/adr/0034-…md:53`), and a wait runs against `OVR-19`'s provider-call deadline and `OPS-33`'s window. (2) needs a bound no requirement gives: the only named polls are `PRV-11`'s order poll and `RSC-41`'s import, neither counted. So continuations spend, and the most the reserve can promise is that no *new* non-exposure-reducing operation is admitted once remaining ≤ reserve. A local count cannot promise even that. Hetzner's bucket is "per Project", "All requests, whether they are authenticated or not, are subject to rate limiting", "the number of remaining requests will increase by 1 every second", and "Burst requests are allowed" (Cloud API reference, Rate Limiting, retrieved 2026-10-10). The operator's console and CLI spend it, so a fixed-period count of provisiond's own requests drifts both ways. `ADR-0036:55` already rejected this shape: "A local count can drift from it in both directions, while a gate closed by the provider's own answer cannot." Every Cloud reply carries `RateLimit-Remaining`; it is the only true value. Residual, stated: operations admitted while remaining exceeded the reserve finish on it, bounded by `PRV-13b`'s worst-case hold; the bucket refills; the stored value lags by the requests in flight. A system path the provider still throttles settles under `OPS-48`, unchanged.

Strongest "don't build this": the reserve exists only because a pre-acceptance throttle on a system delete "is `failed` and stalls the episode" (`OPS-48`). `F48` rejected deferral because "no requirement obliges a driver to report" whether the mutation was sent; `PRV-5` now obliges it: "every driver error MUST carry `details.accepted`". Deferring only an exposure-reducing attempt refused with `accepted: false`, on the provider's Retry-After, removes the reserve, scope and alarm entirely. `F48`'s 2026-10-08 amendment says "The earlier refusal of automatic deferral stands", so this is recorded, not proposed.

**Q19c** — Verdict: at the first claim. `202`, then `failed`, `rate_limited`, `retry_after_ms`, `retryable: true`, zero provider calls, commitment released. No synchronous `429`.

Why. The value moves between enqueue and claim (refill, other tenants, queue depth): Q10's reason, "The cache check runs when a worker claims the refresh, not when it is enqueued." Q17 is the pattern for this kind: a queued create "is checked when a worker claims it, before any provider request … `failed`, `rate_limited`, `retry_after_ms` … `retryable: true` … Its commitment is released in full." A synchronous refusal would still need the claim check, so it is a second surface answering one question twice; `API-50` stays untouched because nothing emits `429`. "Once" is the claim that makes `claim_number` 1: an index refusal "never left `queued` and does not advance the number" (`OPS-6`), and a re-claim after a defer is past the yield phase (`OPS-8`), so every later claim is a continuation, with no new column.

Defects: `02-provider-contract.md:1064-1066` and CNF-337 (`10-conformance-checklist.md:3344`) name no stage or response; CNF-338 (`:3351`) asks for "accounting before each dispatch" and "total available capacity is exhausted", both dissolved.
