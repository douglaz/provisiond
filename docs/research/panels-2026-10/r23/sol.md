**Verdict — Other: positive evidence only.** Keep Cloud’s confirmed block signal, leave Robot to operator notices until its `locked` flag is verified, and retire `none` from the launch enum.

The field’s useful claim is “there is evidence of a restriction,” not “the whole machine is unrestricted.” A clear IP flag cannot make the latter claim. This keeps the useful part of (a); (b) leaves the false-negative path open, while (c) discards Cloud’s documented positive signal. Even this change cannot by itself stop every reinstall loop: an agent can still encounter `unknown`, and [DOM-27](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/01-domain-model.md#L326) explains the intended protection without specifying agent behavior.

- **The Robot story is a valid counterexample to the specification, not a verified account of a live lock.** Hetzner says locks can cover [entire servers](https://docs.hetzner.com/robot/dedicated-server/troubleshooting/guideline-in-case-of-server-locking/). Its [Robot API reference](https://robot.hetzner.com/doc/webservice/en.html) shows `locked` on IPs and subnets, describes it only as “Status of locking,” and lists no server lock field. It does **not** establish that every IP remains `false` during a server lock. If that happens, [PRV-35](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/02-provider-contract.md#L756) permits the driver to treat a clear observation as `none`; [WIR-47](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/13-wire-contract.md#L1153) then refuses the operator’s `disabled` record with `409 state`. The machine view can show `none`, as its [WIR-11 example](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/13-wire-contract.md#L288) does; WIR-47 joins that same machine value into case renderings. The tenant’s timeout and reinstall loop are plausible consequences, not behavior this specification proves.

- **“Is `none` written today?” cannot be answered as a runtime fact:** this repository specifies a system but contains no implementation. [The machine columns](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/05-persistence.md#L268) start at `unknown` with null source and time. The WIR-11 example depicts a provider observation of `none`. WIR-47 gives an operator `disabled` example but specifies neither an operator `none` write nor a clearance verb. [CNF-250](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/10-conformance-checklist.md#L2299) tests the initial nulls; [CNF-233](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/10-conformance-checklist.md#L2622) tests a driver with no signal and the present refusal. Neither tests clear flags against a whole-server lock.

- **Cloud also cannot certify global `none`.** Its [OpenAPI specification](https://docs.hetzner.cloud/cloud.spec.json) defines abuse `blocked` separately for IPv4 and IPv6; either family can be null, and Floating IPs have their own flag. A true flag supports `restricted` for an affected address. It does not establish `disabled` for every route; clear or absent flags do not establish unrestricted networking. The same specification describes `server.locked` as unavailable to the user, without defining it as a network block. Keep that mapping unclaimed pending verification. DigitalOcean’s [Droplet schema](https://github.com/digitalocean/openapi/blob/4a87b3bd8e541f72450c426cf4ba197724b0e479/specification/resources/droplets/models/droplet.yml) describes its `locked` flag as preventing user actions, consistent with [PRV-35’s exclusion](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/02-provider-contract.md#L768).

- **A clear flag and an operator record need separate histories.** A clear provider read should leave the effective value `unknown`, with `provider_api` and an observation time if nobody has recorded a continuing restriction. It must not erase an operator’s whole-server `disabled` notice. A later credible provider `restricted` observation must not downgrade that `disabled` claim; after an evidenced operator release, the provider’s still-positive restriction must remain visible. Store both observations on the *machine* and derive the displayed value. That preserves [DOM-27’s one home](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/01-domain-model.md#L310) and [STO-39’s case cardinality](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/05-persistence.md#L1103), while replacing the absolute precedence asserted in [the storage columns](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/05-persistence.md#L269) and [two-homes reasoning](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/05-persistence.md#L1045). Specify an operator release to `unknown`, not an operator assertion that *all* networking is clear. An old `disabled` otherwise can persist indefinitely; require notice follow-up and expose its observation age rather than silently expiring evidence.

- **The split needs a defined meaning.** Use `restricted` for a confirmed affected route and `disabled` only for evidence that machine networking is disabled. The enum is a machine-level warning, not a per-family inventory. Do not build a per-family public model or an automatic timeout diagnosis without a reader that needs it. This leaves [DOM-7’s separate lifecycle state](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/01-domain-model.md#L315), [LDG-71’s billing and telling rule](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/12-billing-and-ledger.md#L565), and [SEC-41–45’s abuse and account controls](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/07-security-requirements.md#L174) intact; [CNF-228](https://github.com/douglaz/provisiond/blob/82e7f37a7a26223773bbf7931765e35fe1b2b69e/10-conformance-checklist.md#L2616) should still prove billing, visibility and delete on a `disabled` machine.
