**Verdict: (a), with `wind_down_cost` recomposed from parameters the set already has rather than given a new "dispatch→accepted" measurement.**

**Why.** Nothing can write a `billing_stop` sample. `STO-53`'s two writers are "when a resolution (`OPS-27`) establishes when a resource became visible, and when an ordinary mutation's effect is first read back" (`05-persistence.md:479-481`), both visibility, and the formal layer's `Windows` has only `visibility` and `negative` (`tools/formal/Provisiond/Reconcile.lean:96-99`). So `ADR-0018`'s consequence that billing-stop "samples accumulate from the first real mutation" (`docs/adr/0018:47-50`) promised a sample no path produces, and `PRV-13b`'s effective value has been `declared` forever. The only money reader is `PRV-29`'s sizing, "detection interval + measured confirmed-cancellation latency + margin" (`02-provider-contract.md:229`), which never names the field and whose "margin" is defined nowhere. The providers put the stop at the delete itself: Hetzner Cloud "We will bill you for each cloud server until you choose to delete them" and "After you delete the server, you will receive a final invoice" ([FAQ](https://docs.hetzner.com/cloud/billing/faq), [Console cancellations](https://docs.hetzner.com/general/billing-and-account-management/cancellation/cancellations-hetzner-console)); the API delete "immediately removes the Server from your account" and returns an action (`hcloud-go` `ServerDeleteResult{Action}`); Robot "You can only cancel immediately" and "We bill by the hour and never exceed the monthly price cap (except for additional hardware and licenses)" ([Cancellations on Robot](https://docs.hetzner.com/general/billing-and-account-management/cancellation/cancellations-robot)); DigitalOcean "Billing begins when you create the Droplet and ends when you destroy it" ([pricing](https://docs.digitalocean.com/products/droplets/details/pricing/)). What is left after acceptance is the unit, which `ADR-0033` owns. (b) renames `PRV-36`; (c) reads invoices weeks later for a tail smaller than the residual `ADR-0033` already accepted.

**Defects in the framing.**

1. **"Dispatch→accepted latency" is not a measurement and must not become one.** The happy path is one request, bounded by the driver's call deadline; the ambiguous path is `PRV-36`'s effective window plus `OPS-27`'s pass cadence, both existing. But `OVR-19` (`00-overview.md:350-400`) carries store and rescue timeouts and **no provider-call deadline**. Under (a) that row is the term's bound; without it `wind_down_cost` is unbounded on the happy path. This is the gap (a) exposes and the brief misses.
2. **"Billing stops at acceptance" must be read per result, not declared per driver.** `PRV-13c` names "cancellation immediacy and billing granularity" as terms that MUST NOT be constants (`02:395-397`), and `PRV-13` already requires the scheduled driver to "surface the effective cancellation date in its action result" (`02:146-147`). The ADR's wording: the stop is evidenced by the accepted result **carrying no effective date** on a driver declaring the immediate shape. Robot's `now` against a future `earliest_cancellation_date` is still unverified (`08-provider-notes.md:153-157`), so the branch stays.
3. **"The started unit's remainder" is Hetzner-shaped.** DigitalOcean bills per second, its `DELETE` answers `204` 8-25 s before the droplet disappears (`08:302-304`), and the docs do not say whether "destroy" is the request or completion. That tail is seconds at a per-second rate, priced not amplified by `ADR-0033`'s argument, but it is not "the final partial unit" and belongs in `LDG-75`'s accepted gaps (`12-billing-and-ledger.md:1950`) by name.
4. **"The only billing evidence is the invoice … in whole units"** is false for DigitalOcean (per second) and irrelevant: `LDG-75` already trues up invoices; nothing else reads them.
5. **The twenty-sample maximum measures nothing**, not "Hetzner's rounding phase": no engine path yields a sample, and `docs/research/provider-verify-2026-10.md:546-553` already says the invoice carries no latency.
6. **`PRV-29`'s third fact stays.** "Mutation complete, resource absent, and billing stopped are three different facts" (`02:265-267`) still carries `DOM-19`, `PRV-13a` and `SEC-46`. Only its evidence clause changes.
7. **Attachments are covered by (a)** because their stop is their own release: `LDG-38` closes an attachment "at `released_at`" (`12:876-879`), Robot IPs are `api` survivors (`POST /ip/{ip}/cancellation`, billing "based on how long you used the IP or subnet"), and licences bill "for the full calendar months" but the driver orders none (research `:595`). The open hole is `pv-ucs.4` (listing fails), unrelated to the window.
8. **`STO-53.kind` becomes a constant.** One value left; `CNF-75` was withdrawn because "the form is a constant, so the item tested nothing" (`README.md:217`). Drop the column; primary key `operation_id`.
9. **Nothing withdrawn is reintroduced.** The withdrawn table (`README.md:206-258`) has no billing-stop entry. `PRV-36:831-834` is the trap record to keep, dated: it was written on 2026-08-31 because a visibility sample was about to be read as a billing stop. `PRV-29`'s retained text ("the provider with the fastest deletes into the worst `wind_down_cost` bucket", `02:255-258`) argues for (a).
