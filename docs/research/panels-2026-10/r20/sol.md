**Verdict: Other — report whether the resource mutation was rejected, may have taken effect, or was accepted but awaits confirmation.**

The defect is real **for a driver that polls inside create and returns the poll error as the create error**. Hetzner Cloud documents asynchronous actions and `429` responses; Robot documents a `201` order transaction that can remain `in process` while its server number is null. [Cloud API](https://docs.hetzner.cloud/reference/cloud), [Robot Webservice](https://robot.hetzner.com/doc/webservice/en.html). `PRV-5` maps the failing read to `rate_limited`, `not_found`, or `authentication`; `OPS-11` then calls those kinds non-ambiguous and settles the create `failed`. `PRV-11` protects a *timeout* while polling, but not these read errors. `PRV-36` says an early read is not authoritative, but does not change `OPS-11`’s classification. ([02-provider-contract.md:32](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L32), [02-provider-contract.md:113](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L113), [02-provider-contract.md:780](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L780), [03-operation-lifecycle.md:227](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L227), [03-operation-lifecycle.md:249](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L249)).

**Corrections to the framing:**

- This is an allowed failure path, not an inevitable outcome of every accepted order. `OPS-27` also names “the provider accepting the order in its reply” as an entry point for recording a landed order. The contract does not say how a driver exposes that acceptance when its later poll fails. Robot’s verified per-order key covers its auction channel; its standard channel still lacks a verified correlator and requires operator resolution. ([03-operation-lifecycle.md:468](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L468), [02-provider-contract.md:651](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L651), [02-provider-contract.md:738](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L738))
- `details.dispatched` is too broad. Cloud key registration and Robot’s per-order key registration can precede the server order. A definite `4xx` rejection of the order can also follow dispatch. Neither warrants a search for an order that may have landed. A mid-request connection loss is already ambiguous by `network` or `timeout`. A marker written before dispatch cannot settle which side received the request. ([02-provider-contract.md:94](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L94), [02-provider-contract.md:651](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L651), [03-operation-lifecycle.md:249](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L249), [03-operation-lifecycle.md:1226](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L1226))
- On the stated `failed` path, `LDG-32` releases the remaining create commitment. With no machine row, the system has no machine meter. `OPS-32` must *report* an unrecorded server, but must not auto-attach it; `OPS-33`’s negative window and `OPS-36`’s late attach apply to an unresolved create, so they do not repair this failed one. Provider cost can therefore continue until operator action, with no specified automatic bound. The tenant may retain access through its installed SSH key while that server runs; Cloud key-copy timing remains marked `[verify]` in the provider notes. ([12-billing-and-ledger.md:297](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/12-billing-and-ledger.md#L297), [03-operation-lifecycle.md:1342](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L1342), [03-operation-lifecycle.md:1381](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L1381), [08-provider-notes.md:54](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/08-provider-notes.md#L54))
- The exact upfront charge is **not settled by this path**. `LDG-39` says a fee is debited when the order is known to have landed, yet its `needs_reconciliation` row reserves a pending fee, and `OPS-27` groups fee settlement with machine attachment. Robot can have an accepted order before it has a server to attach. `ADR-0033` decides to prepay the first billing unit, but explicitly lists the numbered-requirement edits still owed. Those rules need a coherent accepted-but-pending case; neither (a) nor (b) supplies one. ([12-billing-and-ledger.md:1072](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/12-billing-and-ledger.md#L1072), [03-operation-lifecycle.md:468](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L468), [docs/adr/0033-a-machines-first-billing-unit-is-prepaid-machine-time.md:80](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/docs/adr/0033-a-machines-first-billing-unit-is-prepaid-machine-time.md#L80))

**The other kinds have the same classification gap.** `OPS-45` records dispatch for power, reverse DNS, delete, release attachment, and native rebuild, but `OPS-11` still classifies their later `4xx` by error kind. An accepted release followed by a failed read can settle `failed` without writing `released_at`; its attachment meter and commitment can continue after provider billing stopped. An accepted delete can likewise stall its episode while the local meter continues until a later evidenced gone-write. The marker does not prove `not_applied`, as the persistence note correctly warns. ([03-operation-lifecycle.md:1181](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L1181), [02-provider-contract.md:427](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/02-provider-contract.md#L427), [12-billing-and-ledger.md:312](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/12-billing-and-ledger.md#L312), [05-persistence.md:371](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/05-persistence.md#L371))

**Strongest “don’t build this”:** return an accepted-but-pending result at the mutation response boundary and let existing evidence resolution handle later reads. If polling remains inside a driver, make it preserve that operation-level outcome while retaining `429` as the diagnostic for the read. That avoids a universal dispatch flag, false reconciliation from key uploads, and a second durable create marker. It preserves the one-order and one-correlator decisions; `WIR-35`’s existing create verbs suffice once the operation reaches reconciliation. ([03-operation-lifecycle.md:458](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/03-operation-lifecycle.md#L458), [13-wire-contract.md:864](https://github.com/douglaz/provisiond/blob/3e4b6fa5eaa583d6c7f7c93d6fca6993452b0fb7/13-wire-contract.md#L864))
