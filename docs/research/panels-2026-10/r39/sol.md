**Verdict: reject “pv-ucs.4 has no v1 instance.” The live test narrows the Robot risk, but does not close the generic cleanup gap or justify removing Robot’s survivor declarations.**

The test establishes that this auction server’s `primary_ipv4` and included /64 were absent from the API immediately after cancellation ([live-result.txt:16](<docs/research/panels-2026-10/r39/live-result.txt:16>)). **Defects in the proposal**

- The tested *Primary IPv4* is distinct from the descriptor’s *Additional IP*; the included /64 does not test a separately ordered subnet. Keep both Robot `api` declarations. Neither other datacenters, catalogue contracts, provider termination, nor a hand-added IP was tested ([02-provider-contract.md:189](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/02-provider-contract.md#L189), [provider-verify-2026-10.md:590](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/docs/research/provider-verify-2026-10.md#L590)).
- “No v1 instance” also overlooks the other launch drivers: `OVR-14` says “v1 ships three drivers: Hetzner Cloud, Hetzner Robot and DigitalOcean.” Cloud’s automatically created Primary IP has undocumented `auto_delete`; the descriptor retains its possible-survivor kind ([00-overview.md:246](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/00-overview.md#L246), [provider-verify-2026-10.md:570](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/docs/research/provider-verify-2026-10.md#L570)).
- A future *offer-created survivor* precondition is too narrow. `PRV-45` writes rows only after a gone delete’s listing; `OPS-32` confirms absence only for existing rows. A failed listing, provider termination, or an attachment added between reads can leave zero rows, so `LDG-32` can close while provider rent continues ([02-provider-contract.md:528](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/02-provider-contract.md#L528), [03-operation-lifecycle.md:1368](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L1368), [12-billing-and-ledger.md:308](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/12-billing-and-ledger.md#L308)). `STO-41` records address history, not an attachment identity or cleanup obligation ([05-persistence.md:1230](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/05-persistence.md#L1230)).
- Fable’s tombstone defect is real. `OPS-48` calls a scheduled machine’s date-time tombstone its gone-write, and `Tables.lean` closes on `.tombstone` without a gone observation ([03-operation-lifecycle.md:1072](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/03-operation-lifecycle.md#L1072), [Tables.lean:442](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/tools/formal/Provisiond/Tables.lean#L442)). `LDG-74` explicitly describes “A machine **still present after its date**” whose meter has stopped while the operator still pays ([12-billing-and-ledger.md:548](https://github.com/douglaz/provisiond/blob/dec039f878821929479f136c8a51c797a893d1b8/12-billing-and-ledger.md#L548)).

**Decision and edits**

The strongest case to defer machinery is the observed Robot order path, zero v1 attachment customer rate, and the danger of automatically cancelling an operator’s unrelated asset. The strongest case to build now is the specified Cloud/DO launch scope plus the zero-row loss. Resolve that scope **before sale**: prove each enabled create path cannot leave a billable owned attachment, or implement durable identity capture and automatic reconciliation for paths that can. Recording only during ordinary machine reads is insufficient without a rule for later additions and lost associations. Define whether out-of-band attachments are managed and the operator exposure if they are not; do not substitute a manual cleanup step.
