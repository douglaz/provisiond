**Verdict:** Neither option is complete as written. Add one deletion attempt after a successful create commits *if the key is already eligible*, and keep the sweep for later eligibility or failed cleanup. This reduces the collision window; it cannot guarantee the next same-key create succeeds.

- **The collision premise is conditional.** [PRV-9](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/02-provider-contract.md#L128) permits either a caller’s key or a fresh correlator key under an operation-id name or tag; [PRV-32](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/02-provider-contract.md#L819) requires Robot’s correlator to be unique per order. Robot’s [API](https://robot.hetzner.com/doc/webservice/en.html) rejects an already supplied key, and Cloud’s [API](https://docs.hetzner.cloud/reference/cloud) documents duplicate-fingerprint rejection. A fresh key avoids that collision; registering the *same caller key* again can encounter it. [V9](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/docs/research/provider-verify-2026-10.md#L242) and the [live result](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/docs/research/panels-2026-10/r39/live-result.txt#L7) establish that one deleted key’s fingerprint remained in a transaction. They do not test a second create.

- **Eligibility has no successful-create trigger.** [PRV-9](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/02-provider-contract.md#L128) says when deletion is permitted; [OPS-32](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/03-operation-lifecycle.md#L1460) supplies the sweep path. [CNF-303](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/10-conformance-checklist.md#L2444) tests deletion after the guard clears without assigning a prompt attempt. “Until the next sweep” is also too strong: that pass may still observe `provisioning`, or cleanup may fail.

- **Settlement need not clear the guard.** [OPS-27](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/03-operation-lifecycle.md#L494) requires a direct read confirming the machine exists, not that provisioning ended. Later reads, including [OPS-32’s state observation](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/03-operation-lifecycle.md#L1369), can clear it. A driver inside the create call cannot delete under a rule requiring the operation to have settled.

- **Two existing eligibility clauses need repair.** [PRV-9](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/02-provider-contract.md#L128) both forbids deletion before settlement and requires deletion on pre-acceptance failure; specify when that exception is safe. Its vanished-record exception assumes no produced machine was attached, yet [STO-14](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/05-persistence.md#L1410) deletes settled operation rows while their machines can remain. A missing operation row alone cannot prove the provisioning guard clear.

**Edits:** Put the successful-create rule in PRV-9: after the durable settlement write, attempt deletion once when the confirming machine state is already past `provisioning`; leave the result intact on failure. Otherwise let the sweep act after a later observation. Reconcile the pre-acceptance and retention cases, then update [CNF-303](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/10-conformance-checklist.md#L2444), the [formal eligibility model](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/tools/formal/Provisiond/Rescue.lean#L965), and ADR-0040. Specify that a lost cleanup-delete reply cannot reclassify the committed create; [OPS-12](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/03-operation-lifecycle.md#L301) rules out blind mutation replay, and [PRV-41](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/02-provider-contract.md#L1087) rules out scheduled authentication retries. [OPS-8](https://github.com/douglaz/provisiond/blob/db6bb54ce0460f77cb100d742303622578682089/03-operation-lifecycle.md#L183) serializes per machine, not per account key.

**Strongest “don’t build”:** Don’t add shared-key reuse or a new watcher to promise immediate same-key creates. Reuse would need shared deletion ownership and would compromise Robot’s unique per-order correlator. The existing sweep can observe later state changes.
