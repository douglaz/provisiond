**Verified facts.** `PRV-20` reads as quoted (02-provider-contract.md:719-731). `RSC-3`'s rows and its amended paragraph read as quoted (06-rescue-install.md:82-95). `WIR-20`'s cell reads "Pin caller-supplied full keys" (13-wire-contract.md:681). Only Robot publishes rescue host keys in v1: Cloud "not exposed" (08-provider-notes.md:72), DigitalOcean "not exposed" (08-provider-notes.md:223), Robot fingerprints after boot (08-provider-notes.md:129). Per-boot freshness is `[verify]` (08-provider-notes.md:129; ADR-0041 "Not established"). One field, two names: the wire name is `expected_host_keys` inside `trust` (13-wire-contract.md:681), `API-13` calls it "expected rescue host keys" (04-api-contract.md:961), and 08-provider-notes.md:73 uses `expected_rescue_host_keys`, a name that exists nowhere on the wire. The `trust` object exists only on the two rescue-entering install variants (13-wire-contract.md:672-676) and on rescue-inventory (13-wire-contract.md:960); `RSC-12`/`RSC-13` concern authorized keys injected into the installed OS, not host keys (06-rescue-install.md:135-141). Caller expected keys therefore mean rescue keys only.

**1. Does text decide it?** No. Row 3 says only "They MUST overlap" (06-rescue-install.md:84). The amended paragraph and `CNF-355` state a necessary condition, "MUST match an accepted provider pin, even when a caller key is supplied" (06-rescue-install.md:93-94; 10-conformance-checklist.md:3598-3601), not a sufficient one. `WIR-20`:681 plus row 1 "Pin exactly those" read toward INTERSECTION. The Lean reads the other way: `permitsPresented` at tools/formal/Provisiond/Rescue.lean:168-169 is `(caller ∨ driver) ∧ (¬required ∨ driver)`, which for Robot (`required = true`) reduces to `driver.contains presented`. The model already encodes ANY-PROVIDER-PIN for Robot despite its docstring's "without choosing" (Rescue.lean:157). `CNF-36` covers rows, not this case (10-conformance-checklist.md:224-226).

**2. Reachability.** A caller can know Robot rescue keys only from a prior rescue of the same server, and only if keys are fixed per server. If fresh per boot, every honest both-supplied Robot session fails the overlap check `integrity`; no rule change is needed for that, it already fails closed, and deciding it by fiat would settle a `[verify]`.

**3. Framing check.** The brief says the server "presents its ecdsa key". It does not choose; the client does. SSH kex takes the client's host-key-algorithm preference, and OpenSSH prefers algorithms already in known_hosts. Write only the overlap into the per-operation known_hosts (`RSC-8`, 06-rescue-install.md:115-117) with strict checking and the honest server presents ed25519. Robot already needs a keyscan-then-compare step, since fingerprints cannot populate known_hosts (ADR-0041 "pinning the presented key"); INTERSECTION is that same step with a narrower write. No honest session fails: a server that no longer holds a key it held before is not the overlapping server.

**4. Vote: INTERSECTION.** Public host keys are public. Under ANY-PROVIDER-PIN an attacker who controls the last-rescue record and knows the server's real ed25519 key passes the overlap gate, then presents their own ecdsa key matching their own fingerprint. The caller's keys would have zero bearing on the connection. INTERSECTION makes them bind it. Edits:

- 06-rescue-install.md:84 row 3: "They MUST overlap. Pin exactly the overlapping caller keys. No overlap is an `integrity` failure…"
- 06-rescue-install.md:93-94: replace "MUST match an accepted provider pin" with "MUST match a pinned caller key that an accepted provider pin also matches".
- 13-wire-contract.md:681 and 10-conformance-checklist.md:3598-3601: quote the new sentence; add the case "provider-pinned key not in the caller set is refused".
- Rescue.lean:168-169: `caller.contains presented && driver.contains presented`, plus a `decide` witness refusing `⟨1⟩` for caller `[⟨0⟩]`, driver `[⟨0⟩,⟨1⟩]`.
- 08-provider-notes.md:73: rename to `expected_host_keys`.

**Strongest case for the other side (written on request).** ADR-0041 decided "The presented-key match is what makes the connection safe" and `PRV-20`:730-731 repeats it; the caller's Robot keys can only have come from the same provider record, so they vouch for the record, not an algorithm. The Lean already says ANY-PROVIDER-PIN for Robot, so it is the zero-edit reading. INTERSECTION leans on client negotiation; a non-OpenSSH client or a caller who pasted one of three lines turns a server the provider's own record identifies into a refusal.
