## Q1. Draft: the write chain (engine memory against the store)

**Why not a PostgreSQL marker.** The documentation ties a new timeline to one event: "Whenever an archive recovery completes, a new timeline is created to identify the series of WAL records generated after that recovery" (25.3, Timelines), and to failover: "the timeline change that occurs at failover to another standby" (26.2.4). A frozen-snapshot restore is neither: "when you start the database server on the backed-up data, it will think the previous server instance crashed and will replay the WAL log" (25.2). A standalone `pg_basebackup` ("it is possible to start a postmaster in the target directory without the need to consult the WAL archive") is started the same way unless the operator adds `recovery.signal`. So a timeline or system-identifier check holds for archive recovery, point-in-time recovery and promotion, and misses snapshot and standalone-base-backup restores and a dump reloaded into the same cluster. A cold copy cannot produce the window at all: "The database server must be shut down in order to get a usable backup" (25.2), and a shutdown drops the lock connection, which under R exits every engine. The window therefore needs a hot backup, and the only thing that is certain to differ between a hot backup and a surviving engine is what the engine wrote after it. The draft compares that.

**The mechanism.** A second table holds one row per engine write transaction: the startup generation and a sequence number. The engine remembers the highest number whose commit it has seen acknowledged. Every checked transaction reads that row; a write transaction then inserts its own. A restore returns the table at the backup's rows, so any engine that acknowledged a write after the backup finds its row gone. Reads never contend, inserts never contend, and the advance's `DELETE` waits on nothing new because every share holder of `STO-59` has ended before it runs. Visibility is READ COMMITTED's: "a SELECT query ... sees only data committed before the query began" (13.2.1), and an acknowledged commit precedes the check's query. The compared value has writers other than the engine that checks it, the next pass and the restore, so it is not `CONTEXT.md`'s epoch trap.

### 2. Cost

One table of two columns, one row per engine write per engine lifetime, one in-memory counter. Per write transaction: one index read and one insert, foldable into one `INSERT ... SELECT ... WHERE EXISTS`. The advance gains a `DELETE` and an `INSERT`. New ids: `STO-60`, `CNF-371`. Spans touched: about nine. Lean: a docstring only; if the gate reads `ADR-0025`'s "Every guard that a dated amendment added is a parameter of the model that carries it" as binding here, a `storeRewind` event in `Claim.lean` with the pair `rewound_never_commits` / `rewound_commits_without_check`. Against `ADR-0019`'s objection, the draft keeps a table, a counter and one statement alive, and says so; the counter is compared for presence, never for order, so `STO-59`'s "never compared for order" stays true of the generation.

### 3. Misconfiguration

Restore exposes the store before the record, or omits the record or the fresh value: a survivor with an acknowledged post-backup write is refused at its first write regardless; one without runs on until the fresh value lands, and indefinitely if it never does, as under the Appendix. Clock: unused. Backup older than expected: more rows missing, refused; older than the engine's pass, `STO-59` refuses. Backup newer than the engine's last acknowledged write: the engine's memory is in the store, it continues, and nothing it writes is stale. Wrong database restored: `STO-59` refuses. Chain rows deleted by hand: a false refusal, exit, restart, reseed. Table missing: every write is a store error and `OPS-49` exits; `STO-13`'s schema-version check is the proper refusal.

### 4. Not covered

- The residual: no acknowledged write after the backup. The survivor claims and runs periodic passes before step (1) and step (2) until the record commits. Its writes are consistent with the store, but the freeze is bypassed for that interval.
- Provider calls licensed before the refusal (the Appendix's list).
- Writes that stay on the old server in the two-server shape. They are the second history, outside F7's line, and lost with that server. Writes that reach the restored store are inside the line and refused as above.
- A surviving `api`. It carries no engine memory, so its writes are never stale in G's sense; its hazard is serving step (3)'s window (revived credentials) and `STO-54`'s stop rule covers it for promotion only. An `api` matter, not G's.
- A promotion that is a restore: covered the same way. The promoted standby lacks an acknowledged commit only in the cases `STO-54` lists as restores, and there the chain refuses; the stop rule at 05:1507-1508 is kept, not replaced, and the draft depends on it only for the old-primary side.
- Trace (b): a survivor with no worker in flight writes nothing under R and exits; the fixture holds a worker, as F3 does, and (a) requires one acknowledged write.
